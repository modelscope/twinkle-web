在线学习在训练过程中用当前模型生成回答，再用奖励或教师反馈更新。它与固定回答上的 SFT、固定偏好对上的 DPO 不同：模型变化会改变后续训练样本的分布。本文以 GRPO 说明原理和执行数据流，在线蒸馏也复用其中的采样与训练组件。

## GRPO 原理

GRPO 对每个 prompt 采样多个回答，通过组内相对奖励估计 advantage，不需要额外训练 value model。常用标准化形式为：

```text
A_i = (R_i - mean(R)) / (std(R) + δ)
r_t = p_current(token_t | history) / p_old(token_t | history)
objective_t = min(r_t * A_i, clip(r_t, 1-ε, 1+ε) * A_i)
```

`R` 是同一 prompt 的奖励组，`δ` 是数值稳定项，`ε` 是策略裁剪参数。可选参考模型 KL 项限制相对参考策略的变化，`beta=0` 关闭该项会改变目标，不能当作等价的显存优化。

一组回答奖励相同，组内相对 advantage 就为零。若任务已经饱和或奖励只能区分格式，增加更新步数不会自动产生新的正确性信号。

## 数据流与版本

```text
prompt → sampler 生成 G 条轨迹 → reward → group advantage
      → trainer 计算 log-probabilities → backward / optimizer
      → 更新权重发布到 sampler → 下一批 prompt
```

训练使用生成时的旧策略 log-probability 与当前策略 log-probability 构造 ratio。采样权重版本、回复 token mask 和原 prompt 分组都需要保留。模型生成后的工具观察是上下文，不是动作 token。

SWIFT recipe 组织算法顺序；twinkle model、sampler、reward、advantage 与 StreamingDriver 处理组件执行和调度。当前本机在线 RL 使用 Ray；服务模式通过 twinkle-server 执行模型与采样请求，不需要在客户端持有基础权重。

## 可复制的数学任务

保存为 `prompts.jsonl`，真实训练时扩充问题数量与难度：

```jsonl
{"messages": [{"role": "user", "content": "计算 17×23，把最终答案放在 \\boxed{} 中。"}], "solution": "391"}
{"messages": [{"role": "user", "content": "解方程 2x+3=11，把最终答案放在 \\boxed{} 中。"}], "solution": "4"}
```

`solution` 只传给奖励，不放进模型可见输入。安装 SWIFT 后，为此例安装 vLLM 和数学验证器：

```bash
pip install vllm math-verify
CUDA_VISIBLE_DEVICES=0,1 swift rl \
    --rl_type grpo \
    --model Qwen/Qwen3.5-4B \
    --torch_dtype bfloat16 \
    --attn_impl flash_attention_2 \
    --dataset ./prompts.jsonl \
    --mode ray \
    --nproc_per_node 1 \
    --rollout_sampler vllm \
    --sampler_mode disaggregated \
    --tuner lora \
    --generation_batch_size 2 \
    --num_generations 4 \
    --orm accuracy \
    --beta 0.04 \
    --epsilon 0.2 \
    --max_completion_length 512 \
    --max_length 2048 \
    --vllm_max_model_len 4096 \
    --per_device_train_batch_size 1 \
    --gradient_accumulation_steps 8 \
    --learning_rate 1e-5 \
    --max_steps 100 \
    --logging_steps 1 \
    --output_dir output/online-rl
```

一张卡训练，另一张卡采样。生成 batch 的 prompt 数与每个 prompt 的回答数共同决定轨迹数量，训练 micro-batch 与梯度累积决定更新规模；两者不是同一个参数。`accuracy` 使用 math-verify 对 `solution` 评分，其他奖励不一定需要数学依赖。

## 放置与异步

| 设置 | 控制什么 | 主要条件 |
|---|---|---|
| `sampler_mode=colocate` | trainer 与 sampler 共卡 | 显存需容纳或切换两类工作；可配置 offload / sleep |
| `sampler_mode=disaggregated` | 分配不同 GPU | 为 sampler 留出权重与 KV cache 容量 |
| `async_mode=none` | 同步采样与训练 | 限制权重版本滞后 |
| `async_mode=one_step_off` | 提前一轮采样 | 数据相对当前模型存在版本滞后 |
| `async_mode=fully_async` | 持续重叠采样与训练 | 用 `max_staleness` 限制采样版本差 |

异步可以减少等待，但也改变采样数据的新鲜度。先检查 ratio、KL、奖励和训练吞吐，不把“更忙”直接等同于“更有效”。共卡与分离是资源放置，异步是执行顺序，两者不能用同一个开关描述。

## 奖励、稳定性与评估

自定义奖励合同为 `(completions, **columns) -> List[float]`，支持同步和 async callable，见[插件](/zh/docs/5.0.0.dev/interfaces/plugins)。奖励应覆盖任务正确性并处理超时、无效输出和外部服务失败。Agentic 工具与环境见[Agentic 训练](/zh/docs/5.0.0.dev/training/agentic)。

同时观察 reward、各奖励分项、完成长度、零 advantage 比例、grad_norm、KL 与 ratio 越界比例。loss 可能很小甚至为零，但模型并未因此完成学习。用独立任务集评估最终 checkpoint，保持采样预算和判分器一致。

训练性能回归见[性能说明](/zh/docs/5.0.0.dev/performance)与[曲线](/zh/performance)。全周期、采样和 trainer compute 应分开计时；共卡 v4 全周期不能与分离 v5 的计算段直接计算加速倍数。完整算法入口见 [examples/v5/rl/grpo](https://github.com/modelscope/ms-swift/tree/main/examples/v5/rl/grpo)。
